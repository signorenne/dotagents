This file owns the method's evidence about itself: what the A/B benchmark
measures, how it runs, what limits its numbers, and the metrics summary of
each run. [[file:../DESIGN.org::#method-measured][DESIGN.org#method-measured]] says when it runs;
[[file:architecture.org][docs/architecture.org]] (The evidence tools) describes =tools/benchmark.py=;
the raw runs stay in =.private/evidence/= on the maintainer's machine.

* What it measures

The nexenne method (the global rules, skills, subagents, hooks and path
rules this repository installs) against Claude Code without them, on the
same tasks with the same main model. Per arm: how many runs resolve their
task (the task's hidden tests pass), how many break a test that passed
before (a regression), the cost, the turns, the time, and how often the
agent needed the maintainer. Above all, the quality of each result, which
the hidden tests alone do not show (the maintainer, 15 November 2026):
independent reviewers who do not know the arms judge each change on
solving the issue fully, scope and minimality, code quality and the
repository's conventions, and docs and changelog, and rank the changes of
each task.

* How it runs

- Tasks: SWE-bench Verified (the =SWE-bench/SWE-bench_Verified= dataset,
  test split, 500 tasks), only its two longest difficulty buckets, "1-4
  hours" (42 tasks) and ">4 hours" (3), 45 tasks in 8 repositories. =select=
  chooses them with a seed, one per repository before a second from any.
- Arms: =method=, Claude Code with the maintainer's installed method copied
  into the container and a probe that proves it live (its guard blocks a
  push); =plain=, =claude --safe-mode=, which turns off CLAUDE.md, skills,
  plugins, hooks, MCP servers and custom agents. Both run the same main
  model (Opus 5.5) at effort high, with every permission inside the
  container, the task's own image as the boundary, and WebFetch and
  WebSearch off.
- Prompt: the problem statement, then "Resolve this issue in the repository
  in the current folder. Do not push or open pull requests. When you need
  the maintainer, ask and stop: the maintainer answers your messages." It
  never names the method.
- Simulated maintainer: Sonnet 5.5 on the host, with no tools, answers the
  agent's last message when it stops: it approves a plan that fits the
  issue, takes the option the agent recommends unless it contradicts the
  issue, never writes code, and replies DONE when the agent reports the work
  finished or asks nothing. At most 6 replies a run.
- Grading: the SWE-bench harness (=swebench= 5) runs the task's hidden tests
  on the prediction, the change against the commit the task's image starts
  on (its setup commit after =base_commit=, which the harness patches)
  without the files the hidden test patch touches (the same in both arms).
- Cost: the maintainer sets a cap before each run; each run gets an equal
  share, and each call is capped at what is left of it. Costs are the
  API-equivalent estimate Claude Code reports (=total_cost_usd=); signed in
  with a claude.ai plan, the runs draw on the plan's usage limits instead.
- Full run: at least 20 tasks with three runs per arm. Anything smaller is
  labeled "pilot: not conclusive" and does not count for a version of the
  method.

* Limits

- The tasks are public Python repositories whose fixes a model may have seen
  in training; both arms share that bias.
- The simulated maintainer is a model, not the maintainer: it answers from
  the issue alone and leans toward the agent's recommendation.
- The method arm runs its hooks on a standalone Python 3.12 bound into the
  container, not on the image's own =python3=, and leaves out the
  maintainer's personal settings (model, theme); the rest is the installed
  method as it is.
- WebFetch and WebSearch are off in both arms, so the method's research
  steps cannot run; but both arms have a shell with network access, so
  either could fetch a later release or the upstream repository that holds
  the fix. Each run's record keeps every call's result for a check, and
  only commits reachable from a ref are checked against =base_commit=.
- =--max-budget-usd= checks a client-side estimate: a run can pass its
  share, and the summary counts the runs that did.
- The SWE-bench images add a setup commit after =base_commit=, empty in
  four of the five pilot images; in =astropy__astropy-13398='s it pins
  =setuptools==68.0.0= in =pyproject.toml=. Each run checks that no commit
  after =base_commit= changes a file the task's gold patch or hidden test
  patch changes, so that pin passes; the smoke run, before this check,
  stopped that task's runs as errors (Results). The prediction is taken
  against the setup commit, so the pin is never counted as the agent's.
- Runs go one at a time; a usage limit, an expired login or Ctrl-C stops
  the run; the next start goes on from the stopped run, which starts again
  from the beginning, and the stopped attempt's spend still counts against
  the cap.

- Quality of the pilot's results, 15 November 2026, pilot: not
  conclusive. The maintainer's goal is the quality of the result, not only
  whether the hidden tests pass, so the 20 changes were judged without a
  new run. Per task, one independent reviewer (a Claude Code subagent on
  the agents' model) saw the issue and the task's four changes under
  shuffled labels, with no arm, cost or grade, applied each in a throwaway
  container of the task's image to check its behavior, and scored each 1 to
  5 on the maintainer's rubric (solves the issue fully, judged from the
  issue and the code; scope and minimality; code quality and the
  repository's conventions; docs and changelog where the repository
  expects them), then ranked the four. Unblinded afterwards:

  | arm    | solves | scope | quality | docs | total of 20 | mean rank (1 best) |

  | plain  | 4.50   | 4.60  | 4.50    | 3.90 | 17.5        | 2.90               |

  The method arm's changes scored higher in total on all five tasks, and
  ranked better on three, worse on one (django), equal on one (astropy).
  The gap comes from docs and changelog (a missing release note, an
  incomplete changelog and a wrong whatsnew section in the plain arm) and
  from scope; the fixes themselves solved the issues equally well and were
  of equal code quality. The best astropy change by correctness came from
  the plain arm, the worst (refraction ignored) too. Per run, totals and the
  reviewers' evidence are in the run folder's =quality/= on the maintainer's
  machine. Limits: one reviewer per task and of the agents' own model
  family, 10 changes per arm, small differences (0.9 of 20 points); the
  agents' own tests and their transcripts were not kept, so test quality
  and how the work was done are not judged (kept from 6ad0225 on).
