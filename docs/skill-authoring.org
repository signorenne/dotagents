#+SUBTITLE: how skills in this repository are written and checked
#+OPTIONS: toc:2 num:nil ^:nil
#+STARTUP: showall

This file owns how skills in this repository are written and checked. The
mechanical rules (frontmatter fields, license, characters) are in
[[file:../AGENTS.md][AGENTS.md]] under Hard rules and are enforced by =tools/validate.py=; the rule
behind this guide is in [[file:../DESIGN.org::#concise-skills][DESIGN.org, under Rules that bind]].

* Principles

1. Concise and complete. A skill holds every step and rule a model would
   otherwise get wrong, each stated once, and nothing else. Once a skill
   loads, every token competes with the conversation for the model's
   attention [1][2], and adherence drops as the number of instructions
   grows [3]. Concise does not mean vague: guidance with no concrete signal is
   a failure too [2].
2. Assume a capable model. Do not explain what it already knows (what a PDF
   is, how git works, why tests matter). Give a reason only where the rule is
   not obvious, so the model can apply it to cases the text does not name.
3. The description triggers the skill. Third person, what it does and when to
   use it, in the words a user would type. At most 1024 characters, 200 for
   the claude.ai set. Check it against the descriptions of the other skills so
   two do not compete for the same request. Lead with the user's intent and
   the words they type; method details belong in the body [6]. When another
   skill could take a near-miss request, name it ("Not for X (skill)" or
   "Prefer it over Y"). Claude Code lists descriptions within a budget of
   about 1% of the context window and drops those of the least used skills
   first [4]: keep them short.
4. Specificity follows fragility. Exact steps where a mistake is costly or the
   order matters (commits, deletions, verification); heuristics where context
   decides (design, writing) [1].
5. One default, not a menu. Name the recommended path and, at most, the one
   case that needs another [1].
6. A loop for quality-critical work: produce, check with something that can
   fail, fix, check again [1].
7. Progressive disclosure. =SKILL.md= stays under 500 lines [1]. Bulky detail
   needed only in some runs goes in a file next to =SKILL.md=, linked directly
   from it (one level deep), with what it contains and when to read it.
   Default to a single =SKILL.md=: add a reference file or a script only when
   a real run showed the need. Keep =SKILL.md= under about 5,000 tokens [5]:
   after compaction Claude Code keeps only the first 5,000 tokens of each
   loaded skill, so put the most important instructions near the top and
   write them as standing instructions [4]. =tools/validate.py= fails a body
   over 20,000 bytes, about 5,000 tokens, and holds every =SKILL.md=, subagent
   and the global rules within 10% of the size recorded in
   =tools/size-baseline.json=: growth beyond that is recorded with
   =python3 tools/validate.py --write-sizes= in the same commit, so it is a
   choice the review sees, never drift. A reference file over 100 lines
   starts with a table of contents [1].
8. Consistent terms (one word per concept), no time-sensitive statements, and
   an example only where it shows the expected output better than a rule
   does [1].
9. Portable. Local skills run in Claude Code, Codex, Gemini CLI, Copilot CLI
   and Cursor; the claude.ai set also runs in chat, without a repository,
   shell or subagents. A step that needs a feature one of them lacks says what
   to do there.
10. Wording that holds up in use. Where the model composes text (a plan, a
   report, a note), give a positive recipe of what to write; for a single act
   it must never do, a plain prohibition. Of two wordings that work equally,
   keep the shorter. When a case the stated condition already decides goes
   wrong in a run, answer it by sharpening the condition, not by adding a
   patch for the case. Skills name actions, never one tool's own tool names;
   what differs per tool lives in the installer's tool descriptions.

* Checklist before committing a skill

Review the description and the body against the rubric below, whose
dimensions are those of Tessl's skill review [7]. Each item passes or names
its fix; there is no score, because a total can hide one failing item.

The description, which decides when the skill loads:

- Specificity: it names the concrete actions and what they produce, not a
  category of work.
- Completeness: it says what the skill does and when to use it, in the third
  person.
- Trigger terms: it uses the words a user would type for the request.
- Distinctiveness: no other skill's description claims the same requests, and
  a near-miss names the skill that takes it.

The body, which guides the agent once loaded:

- Conciseness: every step and rule earns its place (would a capable model get
  this wrong without it?), nothing is stated twice, and nothing repeats the
  global rules (=home/.agents/AGENTS.md=).
- Actionability: each step says what to do, with the exact command, path or
  check where a mistake is costly.
- Workflow clarity: a skill with steps runs them in order, each with its exit
  and what to do when it fails, and gives one default path instead of a menu.
- Progressive disclosure: =SKILL.md= holds what every run needs, and detail
  only some runs need sits in a file one level deep, linked with when to read
  it.

Then:

- Nothing contradicts the global rules or a rule in [[file:../DESIGN.org][DESIGN.org]].
- Every skill, subagent, file, command and flag it names exists and works
  (=tools/validate.py= checks only that the paths it names under its own
  folder and =~/.agents/= exist).
- =python3 tools/validate.py=, =python3 -m unittest discover -s tests= and
  =python3 tools/build.py= pass.
- Tested in a real session (below) when the maintainer asks for it; the
  plan file or the pull request says whether it was
  ([[file:../CONTRIBUTING.org][CONTRIBUTING.org]], Workflow).

* Testing a skill

Test with use, not by rereading [1]:

1. Run the skill in a fresh session on a real, small task (the session that
   wrote the skill knows too much to show its gaps), and the same task with
   the skill turned off (in Claude Code, =skillOverrides= set to =off=), to
   see what it adds [1][4].
2. Watch where it goes wrong: a skipped step, a wrong default, a rule it
   ignored, a question it should not have asked.
3. Fix only that, with the smallest change, and run it again.
4. Test on the smallest model the skill will meet (a session runs on the model
   the user picked): what Opus infers, a smaller model may need spelled
   out [1].
5. Check triggering on its own: a few requests that should load the skill and
   near-misses that name another skill's job, each run more than once [6].
