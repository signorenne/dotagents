# Design

Goal: a design that the build skill carries out plan by plan, in this session or a fresh one, readable without this conversation. Write no source code; the only files written are the design and, with the user's approval, decision-log entries. A rule change the user approves is written in the design with its exact text and applied by the plan that builds it.

1. Map the area: delegate to scout with the feature (return: its standard brief, at most 60 lines). Re-read a file yourself only when a detail decides the design.
2. Location and format: the project's own design or spec workflow when it has one (it wins where it conflicts with this skill); otherwise .private/designs/<slug>.<ext> in the project's prose format (in a linked worktree, the main checkout's .private/; when .private/ is not git-ignored, ask once where designs go). Sections: objective; non-goals; affected areas (paths); public surface; decisions (each with the accepted decision-log entries it relies on, by id); behavior and edge cases; unchanged behavior as WHEN <condition> the system SHALL CONTINUE TO <behavior>, each with the test that pins it (path and name); acceptance criteria as observable behaviors a test or command can fail, observed where the effect is consumed; plans, in order.
3. Settle the open design choices: first the assumptions table (evidence, what breaks if wrong, how sure), then ask the questions whose answers change the design through the tool's question interface when it has one (in Claude Code AskUserQuestion): one question per item, its options with their consequences and the recommended one first, at most four per call and more in further calls, a dependent question after the answer it depends on (decide skill for each hard one), until the remaining unknowns would not change it.
4. Write it. Name exact files, types, functions, error behavior and commands, each checked against the current code. For each mechanism a plan relies on, its early returns, guards, preconditions and the code that runs before it, and why the effect happens, with file:line. A plan that changes a value searches the tests for it and its derived values, and its failing test must fail at run time, not stop the build. A destructive or safety decision uses the code's own conservative predicate. No "as discussed". Each plan entry: its scope, the acceptance criteria it owns, its lane and risk grade, what it depends on, and the interface it produces for the plans after it.
5. Check it with an agent that did not write it (general subagent told not to edit; elsewhere the reviewer told the target is the design file and its checks apply to the design's claims, while you check the external facts; return: findings, at most 60 lines). First, from the design alone and before opening any other file, it writes what the design proposes and how the code works according to it: a wrong paraphrase, or a section it cannot paraphrase, is a finding. Then it checks every file, symbol, signature, command and external fact against the code and the installed version of each tool, applies step 4's rules (mechanisms with file:line, values searched in the tests, failing tests that fail at run time, conservative predicates, criteria observed where the effect is consumed), names each requirement no test could fail or that conflicts with another, and gives a second reading of each acceptance criterion that has one. Fix the design. A criterion with two readings is a question: ask which is meant, then reword it. Show the user any change to a requirement or decision they already settled before keeping it. Record the commit the check ran on (git rev-parse HEAD).
6. Decisions: for each choice that meets the decision log's recording bar, draft an entry and ask whether to add it; write it Accepted only after explicit confirmation, otherwise Proposed.
7. Reply opening with one line: Done: yes (the design is written, no code changed) or Done: no, and what is left for the user and for you. Then the design path, the plans in order with their lanes, the open questions, and the next step as the exact prompt to paste, in a fenced block: it runs build on the first plan of the design, pasted here to go on in this session or in a fresh one when the context is long. When the user asked to build too, run build on the first plan now instead.
