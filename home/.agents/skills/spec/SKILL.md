# Spec

Goal: a spec that a fresh session, with no access to this conversation, can implement correctly. Write no source code in this session; the only files you write are the spec and, with the user's approval, decision entries; a rule change in an owning doc that a decision reaches is applied in the implement session, not here (step 6).

1. Map the area: delegate to scout with the feature description and ask for its standard brief. Re-read a file yourself only when a detail decides the design.
2. Follow the project's spec workflow when it has one (for example a "Spec workflow" section in its agent workflows doc). It defines the location and the sections, and its steps add to this skill's; where they conflict, the project's workflow wins. If the project has none, write to .private/specs/<slug>.<ext> when .private/ is git-ignored (otherwise ask once where specs go), in the project's prose format, with these sections: objective, non-goals, affected areas (as paths), public surface, reuse, behavior and edge cases, unchanged behavior, deliverables (tests, examples, docs), decisions, acceptance criteria, verification commands (the narrowest check each step runs, which takes seconds or minutes, and the full gates, run once on the final commit), open questions.
3. Settle each open design choice with the decide skill, until the remaining unknowns would not change the design.
4. Write the spec. Name exact files, types, functions, error behavior and commands, all checked against the current code. For each function or mechanism a step relies on, read its early returns, guards, preconditions and required state, and the code that runs before it (initialization, registration), and state why the step's effect happens, with file:line. When a step changes a value, search the tests for it and its derived values; the planned failing test must fail at run time on the unchanged code, not stop the build. A destructive or safety decision uses the code's own conservative predicate when one exists. Write each acceptance criterion as an observable behavior that a test or a command can fail, observed where the effect is consumed, not a proxy that can hold without it; compared measurements come from one session with known run-to-run spread. For a change to existing behavior, list under unchanged behavior each behavior the change could plausibly break that must stay as it is, as WHEN <condition> the system SHALL CONTINUE TO <behavior>, each with the existing or new test that pins it (path and name); implement runs those tests in its baseline and its gates. No "as discussed", no references to this conversation.
5. Verify the spec before handing it over. Delegate it to a subagent that did not write it (in Claude Code the general-purpose subagent, told it must not edit anything; elsewhere the reviewer subagent, told that the review target is the spec file at its path, not a diff, and that its checks apply to the spec's claims, while you check the external facts yourself because it has no web access; without subagents, do it yourself following ~/.agents/agents/reviewer.md after re-reading each source). Ask it first to write, from the spec alone and before opening any other file, what the spec proposes and how the current code works according to it; compare that paraphrase with what you meant: a wrong paraphrase, or a section it cannot paraphrase, is a finding (the spec is ambiguous or incomplete there). Then ask it to check every file, symbol, signature, command and external fact the spec names against the current code and the cited documentation, and each fact about an installed tool's files, paths or output against that installed version (its source or one run), since documentation drifts from the version in use, to apply step 4's effect, value, decision and evidence rules, spelled out in its brief, to report each claim that is wrong or unverifiable with its evidence, to name each requirement that no test or command could fail or that conflicts with another, and to give, for each acceptance criterion, a second plausible reading when one exists that would lead to different code or tests. Fix the spec. A criterion with two readings is a question for the user: ask which one is meant, then reword the criterion so only that one remains. Before keeping any change to a requirement or decision the user already settled, show it to the user. Record in the spec the commit the check ran on (git rev-parse HEAD), so implement can tell whether the code changed since.
6. Decisions: list by id the Accepted entries the spec relies on and the entries decide recorded in step 3. For a choice settled outside decide that meets the decision log's recording bar, draft an entry and ask whether to add it; write it as Accepted only after explicit confirmation. Put each rule change the user approved in the spec's deliverables, with its exact text and the doc that owns it, so implement applies it without a second approval; a rule change the user did not approve is recorded as Proposed.
7. Stop. Reply with the spec path, the open questions, and the next step: start a fresh session (in Claude Code: /clear) and run the implement skill on the spec path.
